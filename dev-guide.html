Developer guide

Everything a new developer needs on day one, and what everyone follows every day after. If this page and the code disagree, fix one of them in the same pull request.

Day one

  1. Read the Overview, the Glossary and the invariants.
  2. Set up the local stack (below) and run all tests.
  3. Walk through one sale: scan → complete → sync → server allocation → report, using Offline & sync and Key flows next to the code.
  4. Pick a ticket labelled good-first-issue.

Local setup

Prerequisites: Git, Docker Desktop, JDK 25 (Temurin; the Gradle wrapper downloads it if it is missing), Node 22 LTS + pnpm 9, an IDE (IntelliJ IDEA or VS Code). Optional: an 80 mm ESC/POS printer or a network printer emulator.

git clone <repo-url> retailos && cd retailos
cp infra/.env.example infra/.env            # local-only secrets, never commit .env
docker compose -f infra/docker-compose.yml up -d   # postgres:18, minio, mailpit
./backend/gradlew -p backend bootRun --args='--spring.profiles.active=local'
pnpm install
pnpm --filter admin dev                      # http://localhost:5173
pnpm --filter register-electron dev          # opens the register window
pnpm seed                                    # demo tenants: "Lanka Retail" and "City Pharmacy"

Demo logins and enrollment codes are printed by the seed script and stored in infra/seed/README.md. Never use real credentials locally.

Java conventions (backend)

  • Package by module: com.devcity.retailos.<module>. Only the module root, events and spi packages are public. Everything else lives in internal. The build checks this; see Module boundaries.
  • Layers in every module: controller (web/) → service (service/) → repository (repository/), with entities in model/ (ADR-015, Layers inside a module). Business rules live in services, never in controllers.
  • Use BigDecimal for money with the shared Money type (scale 4, RoundingMode.HALF_UP). double/float for money fail the ArchUnit test (INV-03).
  • Use records for DTOs, commands and events. Events are immutable and versioned (SaleCompletedV1 when the shape must change).
  • One transaction per public service method (@Transactional); read methods use readOnly = true. Never call a remote service inside a transaction.
  • Validate at the edge (Bean Validation on DTOs), and enforce business rules in the service.
  • Errors: throw a DomainException with an error code from the catalog. A global handler maps it to a Problem Details response.
  • Formatting: Spotless (google-java-format). Null-safety with JSpecify annotations.

TypeScript conventions (admin and register)

  • strict: true, no any (lint error), and zod schemas at the edges (API responses, local DB rows).
  • Money and quantity use Decimal from decimal.js, serialised as strings. A lint rule flags arithmetic on money fields.
  • register-core has no React or shell imports (an ESLint boundary rule enforces this).
  • Server state goes through TanStack Query with the generated client. UI state uses React state or Zustand for the register cart. Don't keep global mutable singletons.
  • Every user-visible string uses t('key') with keys in packages/i18n/{en,si,ta}.json. CI fails on missing keys in any language.
  • Components: functional, typed props, and accessible (labels, focus order, large touch targets on the register: at least 44 px).
  • Register UX rules: every action is reachable from the keyboard, no confirmation dialog for routine actions, errors are shown inline in plain language (si/ta/en).

Git workflow

  • Trunk-based, no develop branch: short-lived branches named <type>/<module>/<ticket>-<short-name> (e.g. feat/iam/AUTN-09-refresh-rotation), merged to main by PR within a few days. Unfinished work goes behind a feature flag. See Branches & naming.
  • Conventional Commits: feat(sales): record batch hint from GS1 scan. These generate the changelog.
  • Every PR: CI green, self-review against the checklist below, and a link to the requirement ID (F-103, BR-04…).
  • Each app has its own release tag: backend-v1.4.0, admin-v1.3.0, register-v1.6.0 (both register shells share one version). The tag builds the release.
  • Squash merge only, so main has one commit per pull request. Branch protection, CI path filters and the GitHub settings are in Repository & GitHub.

Definition of done

  • Acceptance criteria from the user story pass as automated tests.
  • Works offline on the register (if it's a register feature) and survives an app restart.
  • Strings translated to si/ta (machine draft allowed, marked for review).
  • Permissions checked on the server, and audit entries added for money, stock and permission actions.
  • Migration is expand-only, and the API change is additive (or ADR + /v2).
  • Metrics and logs added for new failure modes, with a runbook entry if support could hit it.
  • Docs updated: module page, data model, flows, and this site's search index (pnpm docs:index).

Walkthrough: adding a feature end to end

Example: F-209 near-expiry discount suggestion.

  1. Spec: add acceptance criteria to the requirement (or ticket). Decide which module owns it: inventory (expiry) + pricing (suggestion).
  2. Schema: V2027_02_10_1__near_expiry_rule.sql adds a near_expiry_rule table with tenant_id, RLS policy and indexes. Add it to TenantIsolationIT.
  3. Service: NearExpiryPolicy, a plain class used by PriceService in pricing/internal/service, with unit tests and test vectors. The repository and entity go in repository/ and model/.
  4. API: GET/PUT /api/v1/pricing/near-expiry-rules with permission price.edit. Regenerate the OpenAPI client.
  5. Sync: add the rule to the prices scope in sync_change_log writes, and the local SQLite table + migration in register-core.
  6. Register: the cart engine applies the suggestion. The UI shows a badge. i18n keys go in all three languages.
  7. Admin: settings screen to edit rules.
  8. Observe: counter metric near_expiry_discount_applied_total.
  9. Docs: update Modules, Data model and Requirements status.

Debugging locally

  • Backend: run with the local profile for SQL logging (logging.level.org.springframework.jdbc.core=DEBUG and Hibernate SQL). The Actuator endpoint /actuator/modulith lists modules and events.
  • Register: Ctrl+Shift+D opens the developer panel (debug builds only): local DB browser, outbox queue, sync log, device bridge simulator (fake printer writes PNG receipts to ./tmp/receipts).
  • Offline testing: the developer panel has a Simulate offline toggle. For a real test, block the backend port in the firewall.
  • Clock skew: REGISTER_FAKE_CLOCK=2026-12-31T23:59:00+05:30 tests business-date rollover.
  • Production issues: follow Trace a sale end to end. Never connect to production with a superuser for reading. Use the support console or a read-only role.

Code review checklist

  • Which invariants does this touch? Are they tested?
  • Does any module read another module's table or internal class?
  • Money: decimals only, rounding as BR-03?
  • Can this fail offline? What does the cashier see?
  • Is it safe to retry (idempotent)? Safe to run on two instances (ShedLock)?
  • Tenant ID in every query, cache key and job payload?
  • N+1 queries, missing indexes, unbounded lists (pagination)?
  • Logs free of secrets and personal data?
  • Security checklist in Security passed?
