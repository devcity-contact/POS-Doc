System architecture

RetailOS has three deployable parts: a modular monolith backend, an admin web app, and a register app packaged for Windows and Android. This page shows how they fit together, from the outside in, following the C4 model.

Architecture principles

#PrincipleWhat it means in practice
P1The till never stopsAnything a cashier does works offline. The network is for syncing, not for selling.
P2Facts are immutableSales, payments, stock movements and audit entries are only ever appended. Corrections are new records (INV-02, INV-04).
P3One deployable, many modulesOne backend process with strict internal boundaries. No microservices until a measurement justifies one (INV-08).
P4Core stays genericIndustry behaviour lives in extension modules that plug into named extension points.
P5Boring, portable infrastructureContainers, PostgreSQL and S3-compatible storage. No vendor-only services in the core path.
P6Secure by defaultTenant isolation in the database, least privilege, encrypted at rest and in transit, audit everything that touches money.
P7Observable from afarEvery register and request can be traced remotely by sale UUID, register ID and trace ID.
P8Simple until proven otherwiseBuild Redis, Kafka, Kubernetes, CQRS read stores or WebSockets only when a measured need appears. Record the trigger in an ADR.

Inside the register app

The register is where most of the complexity sits, because it must behave correctly with no server. It is built in layers so the business logic is shared by both shells and can be tested in plain Node.

Register design rules

  • register-core has no React, DOM, Electron or Capacitor imports. It runs under Vitest in Node.
  • Ports are TypeScript interfaces: LocalStore, DeviceBridge, Clock, IdGenerator, SyncTransport. Each shell provides adapters. Tests use fakes.
  • Electron security: contextIsolation: true, nodeIntegration: false, sandbox: true. The renderer reaches native code only through a typed IPC allowlist exposed by preload.ts.
  • All money math uses decimal.js (INV-03). Tax and price calculations are tested against shared/test-vectors/*.json, the same files the Java tests use, so the register and server can't disagree.
  • The UI never writes SQL. Screens call core use cases, and use cases call the store.

Inside the backend

One Spring Boot application, split into modules under com.devcity.retailos.<module>. Spring Modulith checks in CI that no module reaches into another's internals (INV-08).

Layers inside a module

Complex modules (sales, inventory, pricing, tax, sync) use a light hexagonal layout. Simple CRUD modules use controller → service → repository. Don't force four layers on a categories table.

sales/
├─ SalesApi.java            ← public interface other modules may call
├─ events/                  ← public events (SaleCompleted, SaleReturned)
├─ spi/                     ← extension points industry modules implement
└─ internal/                ← NOT visible to other modules
   ├─ web/                  ← REST controllers, DTOs, mappers
   ├─ application/
   │  ├─ command/           ← writes: RecordSaleHandler, ReturnItemsHandler
   │  └─ query/             ← reads: SalesHistoryQuery (SQL → DTO)
   ├─ domain/               ← Sale, SaleLine, policies; no Spring imports
   └─ persistence/          ← JPA entities / JdbcClient repositories

Reads and writes (CQRS-lite)

Inside a module, changing data and reading data take different paths, but they use the same database and the same tables. This is a light form of CQRS: it keeps the code clean without a second store.

Commands (writes)Queries (reads)
ExamplesRecord a sale, post a goods receipt, adjust stock, close a shiftSales history, stock on hand, dashboard, reports, look-ups for screens
PathController → command handler → domain objects → repositoryController → query → SQL (JdbcClient) → DTO. Domain objects are not loaded.
Rules checkedAll of them: totals, tax (INV-07), stock only through movements (INV-04), limits, approvals, auditNone needed: a query never changes data
TransactionRead-write, one per command (one per item for sync push)@Transactional(readOnly = true); can later run on the read replica
TestsDomain unit tests plus integration tests of the handlerIntegration test against Testcontainers with realistic data; check the query plan for big tables
Tenant isolationThe same for both: row-level security on every query (INV-01), covered by TenantIsolationIT.

Rules

  • A query never writes, and a command never returns a list for a screen. A command returns the id or a small result; the screen then calls a query.
  • Simple CRUD modules (categories, suppliers, units) don't need the split. A service with get and save methods is fine.
  • Queries stay inside their module. A screen that needs data from several modules uses the reporting module's views, not joins into another module's tables (INV-08).
  • When a read gets slow, go one step at a time: add an index, then a materialized view, then the read replica. A separate read store or event sourcing needs a measured reason and an ADR (principle P8).

Not used: full CQRS with a separate read database, or event sourcing. Sales are already stored as facts that are never edited (INV-02). A second store would add out-of-date reads, keeping two copies in sync, and row-level security set up twice, with no gain at this size.

How the architecture evolves

Repository layout

One monorepo, so one developer (or an AI agent) can change the API, the register and the docs in a single commit.

retailos/
├─ backend/                     Spring Boot app (Gradle)
│  ├─ src/main/java/com/devcity/retailos/{platform,catalog,pricing,inventory,sales,...}
│  ├─ src/main/resources/db/migration/   Flyway V001__*.sql
│  └─ src/test/…                 unit, Modulith, Testcontainers tests
├─ apps/
│  ├─ admin/                    React admin web (Vite)
│  ├─ register/                 React register UI
│  ├─ register-electron/        Windows shell (main, preload, device adapters)
│  └─ register-android/         Capacitor shell + native plugins
