Module boundaries

The backend is one application split into 15 business modules plus platform. A module may use only the public parts of another module: its *Api, its events and its spi. Everything in a module's internal package is private. A test reads the compiled code on every build and fails the build when a rule is broken (INV-08).

In one sentence The package structure decides what a module is, two annotations decide what is public, and ApplicationModules.verify() checks every dependency. Built in SET-04 (the modules) and SET-05 (the check).

The picture

1 · Every top-level package is a module

Spring Modulith starts from the package of the main class, com.devcity.retailos (where RetailOsApplication lives). Every package directly below it is one module. There is no list to keep up to date: a new top-level package is a new module on the next build.

com.devcity.retailos
├── RetailOsApplication.java
├── tenancy/  iam/  devices/  audit/                    store & staff
├── catalog/  pricing/  tax/                            catalog & pricing
├── inventory/  purchasing/                             inventory
├── sales/  payments/  cash/  customers/                sales & money
├── sync/  reporting/                                   edge
└── platform/                                           shared kernel (open)

What each module owns and offers is on Backend modules. A test (ModuleLayoutTest) checks that Spring Modulith finds exactly these 16 modules, so a package added at the wrong level is caught.

2 · What is public and what is private

Spring Modulith's rule: a module's root package is public; every sub-package is private unless it is marked as a named interface. RetailOS uses the same layout in every module (ADR-015):

com.devcity.retailos.sales/
├── package-info.java   @ApplicationModule          root package: PUBLIC  (SalesApi lives here)
├── events/             @NamedInterface("events")   PUBLIC: SaleCompleted, SaleReturned, SaleException
├── spi/                @NamedInterface("spi")      PUBLIC: SaleLineValidator
└── internal/           (no annotation)             PRIVATE to sales
    ├── web/            controllers
    ├── service/        SaleService: business rules, implements SalesApi
    ├── repository/     JPA repositories, JdbcClient queries
    └── model/          entities
PackageMarked withVisible to other modules?What goes in it
Module root, e.g. sales@ApplicationModule in package-info.javaYesThe *Api interface and the records it takes and returns. Nothing else.
events/@NamedInterface("events")YesEvent records the module publishes, e.g. SaleCompleted. Only in modules that publish events.
spi/@NamedInterface("spi")YesInterfaces other code implements to plug in, e.g. SaleLineValidator for industry extensions. Only in sales and pricing today.
internal/ and everything belownothingNoControllers, services, repositories, entities, helpers. Free to change without breaking another module.

The root package-info.java of sales as it is in the code:

/**
 * Sales module.
 *
 * <p>A completed sale is a fact: never rejected, updated or deleted (INV-02).
 * <p>Owns tables: sale, sale_line, sale_line_allocation, sale_return, …
 * <p>Other modules use it only through SalesApi in this package, its events and its spi (INV-08).
 */
@ApplicationModule(displayName = "Sales")
package com.devcity.retailos.sales;

import org.springframework.modulith.ApplicationModule;

And sales/events/package-info.java:

@NamedInterface("events")
package com.devcity.retailos.sales.events;

import org.springframework.modulith.NamedInterface;
Why the Api is an interface SalesApi is an interface in the public root package; SaleService in internal/service implements it. Other modules only ever see the interface and the records it uses, so sales can rename, split or rewrite its services and entities without touching any other module. Never return an entity from an Api: return a record.

3 · platform is open to everyone

platform is the shared kernel: money and quantity types, ids, the clock and business date, JSON settings, error responses, request context and the tenant-aware transaction set-up (CORE-01 to CORE-14). Every module needs these, so platform is an open module: all of its packages are public.

@ApplicationModule(displayName = "Platform (shared kernel)", type = ApplicationModule.Type.OPEN)
package com.devcity.retailos.platform;

It works in one direction only: extensions → core modules → platform (dependency rules). platform has no business rules and no tables, and it may not use any business module. A separate test checks this, because "open" would otherwise let it slip through.

4 · The check

ModularityTests (in backend/src/test/java/com/devcity/retailos/) loads the modules from the compiled classes and checks them:

class ModularityTests {

    static final ApplicationModules modules = ApplicationModules.of(RetailOsApplication.class);

    @Test
    void modulesOnlyUseEachOthersPublicParts() {
        modules.verify();                                     // INV-08
    }

    @Test
    void platformDependsOnNoBusinessModule() {
        var platform = modules.getModuleByName("platform").orElseThrow();
        assertThat(platform.getDirectDependencies(modules).uniqueModules()).isEmpty();
    }

    @Test
    void writesTheModuleDocumentation() {
        new Documenter(modules).writeDocumentation();         // build/spring-modulith-docs
    }
}

The rules it applies

RuleFails on, for exampleChecked by

What counts as "using" another class

The check reads the bytecode with ArchUnit, so it sees every real dependency, not only import lines:

  • calling a method or a constructor, reading a field
  • a field, parameter, return or local variable of that type
  • extending a class or implementing an interface
  • an annotation, a generic type argument (List<StockService>), an exception that is thrown or caught

It does not see classes reached by name at run time (reflection, Class.forName), or tables read with SQL. See what it doesn't cover.

5 · What a failure looks like

While building SET-05, a temporary class in sales/internal/service called a class in inventory/internal/service. The build failed with:

ModularityTests > modulesOnlyUseEachOthersPublicParts() FAILED

org.springframework.modulith.core.Violations:
- Module 'sales' depends on non-exposed type
  com.devcity.retailos.inventory.internal.service.TempStockService within module 'inventory'!
  Method <com.devcity.retailos.sales.internal.service.TempSaleService.x()> calls method
  <com.devcity.retailos.inventory.internal.service.TempStockService.onHand()> in (TempSaleService.java:3)

It names the module that broke the rule, the private class it reached, and the file and line. Once the class was removed, the check passed again.

How to fix one

You need…Do this
an answer from the other module now, in the same transactionAdd a method to its *Api interface (taking and returning records), implement it in its internal/service, and call the Api.
to react to something that happened in the other moduleListen to its event in events/ with @ApplicationModuleListener. If the event doesn't exist yet, the owning module adds it.
a small shared type (Money, an id, a date helper)Put it in platform, if it holds no business rules.
the other module's entityDon't. Ask its Api for a record with the fields you need.
Never "fix" it by making a package public Adding @NamedInterface to internal or one of its sub-packages makes the error go away and the boundary disappear. A new named interface is a design change: discuss it in the pull request.

6 · Crossing a boundary the right way

Both paths only touch public parts. Which one to use (dependency rules, events):

Call the *ApiPublish and listen to an event
Use whenyou need the answer now, inside the same transactionthe work can happen after the transaction commits
ExampleInventoryApi.allocateAndDeduct(): money and stock must never drift apartSaleCompleted → customer visit stats, daily totals, notifications
If the other side failsthe whole transaction rolls backthe sale stays recorded; the event is retried from the outbox (ADR-007)
Who depends on whomcaller → the called modulelistener → the publisher's events package
 
// sales/internal/service/SaleService.java   (sales → inventory: allowed, InventoryApi is public)
@Transactional
public SaleResult recordSale(RecordSale command) {
    var allocation = inventoryApi.allocateAndDeduct(command.lines());   // same transaction
    var sale = sales.save(Sale.from(command, allocation));
    events.publishEvent(new SaleCompleted(sale.id(), sale.customerId(), sale.total()));
    return SaleResult.of(sale);
}

// customers/internal/service/CustomerStatsListener.java   (customers → sales.events: allowed)
@ApplicationModuleListener
void on(SaleCompleted event) {
    stats.recordVisit(event.customerId(), event.total());               // after commit, retried
}

8 · How we know the check works

A check that never fails proves nothing, so ModularityGuardTest runs it on a small, deliberately broken example and expects it to fail. The example lives in com.devcity.modulithfixture, outside the real modules, so it can't affect them:

com.devcity.modulithfixture
├── orders/OrderService.java              uses stock.internal.StockRepository   ✗
└── stock/
    ├── StockApi.java                     the public way in, which OrderService ignores
    └── internal/StockRepository.java     private to stock
@Test
void failsWhenAModuleUsesAnotherModulesInternalPackage() {
    ImportOption includeTestClasses = location -> true;    // the fixture is compiled with the tests
    var fixture = ApplicationModules.of("com.devcity.modulithfixture", includeTestClasses);

    assertThatThrownBy(fixture::verify)
            .isInstanceOf(Violations.class)
            .hasMessageContaining("OrderService")
            .hasMessageContaining("internal.StockRepository");
}

If a library upgrade or a configuration change ever stopped the check from working, this test would fail first.

9 · Architecture rules inside a module

The boundary check looks between modules. A second set of ArchUnit rules (SET-06) looks inside them. They live in backend/src/test/java/com/devcity/retailos/ArchitectureRules.java, run in ArchitectureTest (so in test and modulithVerify), and each has a bad example in com.devcity.archfixture that ArchitectureGuardTest expects to fail.

10 · Generated module documentation

Each run of the check also writes Spring Modulith's own documentation to backend/build/spring-modulith-docs/:

  • components.puml: all modules and the dependencies between them (C4 component diagram, PlantUML)
  • module-<name>.puml: one module and its direct neighbours
  • module-<name>.adoc and all-docs.adoc: a canvas per module listing its public types, events and Spring beans

They show the dependencies as they are in the code, so compare them with the planned module map. They are build output and are not committed.

11 · What it doesn't cover

Not checkedCovered instead by
SQL that reads another module's tablesOwnership is in the data dictionary and checked in review. Tenant isolation is enforced by the database itself (row-level security, DB-08).
Reflection or lookups by class nameNot used in normal Spring code; the review checklist flags it.
"Api only when the answer is needed now, otherwise events"A design choice for review (dependency rules). The rules do check that only services call other modules.
Which modules may call whichToday any module may use any other module's public parts. See making it stricter.
Field types, naming, double for money, layersThe architecture rules (SET-06).

12 · Making it stricter later

A module can list the only modules it may use. The same verify() then also fails on any other dependency:

@ApplicationModule(
        displayName = "Catalog",
        allowedDependencies = { "platform", "tax", "audit" })     // catalog may never call sales
package com.devcity.retailos.catalog;

Named interfaces can be named precisely too, e.g. "sales :: events" lets a module use the events of sales but not SalesApi. We add these once the real calls between modules have settled. Each one is a short change with a review.

13 · Checklist

Adding code to a module

  • Controllers, services, repositories and entities go in internal/web, internal/service, internal/repository, internal/model.
  • Something other modules must call goes on the module's *Api interface, with records in the root package.
  • An event goes in events/, as an immutable record (SaleCompletedV1 when its shape must change).
  • Run ./gradlew modulithVerify before pushing.

Adding a module

  • Create com.devcity.retailos.<name> with a package-info.java carrying @ApplicationModule and what the module owns.
  • Add internal/{web,service,repository,model}, and events/ or spi/ with @NamedInterface if needed.
  • Add it to ModuleLayoutTest, the module map (tools/build_module_map.py) and, for new tables, the data dictionary. A new module is an architecture change: record it in an ADR.
