Monitoring & runbooks

You can't drive to every shop. RetailOS is built so that most problems can be seen, diagnosed and often fixed remotely: every register reports its health, every sale can be traced end to end, and every common failure has a runbook.

Observability stack

Logging rules

  • Structured JSON to stdout with these fields: ts, level, msg, traceId, spanId, tenantId, branchId, registerId, userId, saleId, code.
  • Log WARN or higher for every SaleException, BLOCKED outbox item, RLS error and auth failure burst.
  • Never log PINs, passwords, tokens, full phone numbers, prescription details or request bodies of auth endpoints.
  • Retention: 14 days hot, 90 days archived (compressed) for audit-related logs. The audit log itself lives in the database.

Support console

An internal page in the admin app, visible only to PLATFORM_SUPPORT with tenant consent. It shows:

  • Per register: app version, last heartbeat, last successful pull and push, pending and blocked outbox counts, printer status, free disk space, clock skew.
  • Actions: request log upload, force full resync, requeue blocked items, lock device, reset receipt sequence (two-person approval).
  • Per tenant: open sale exceptions, import job errors, fiscal submission status, enabled modules, plan.

Debugging: trace a sale end to end

Every sale carries its UUID and a traceparent from the moment it's created on the register. Use either one to follow it.

  1. Start from the receipt. Receipt CMB01-R02-000154 → admin: Sales → search receipt. If it's found, you have the sale ID, received time and exceptions.
  2. Not on the server? Support console → register R02 → outbox. Is the sale PENDING (network), BLOCKED (see last_error), or missing (it was never completed: check local logs)?
  3. Server logs: search saleId=<uuid> or traceId. You'll see the push request, idempotency result, allocation and published events.
  4. Stock looks wrong? Query stock_movement where ref_type='SALE' and ref_id=<saleId>, then compare with sale_line_allocation.
  5. Totals look wrong? Re-run the line through shared/test-vectors tooling: ./gradlew taxCheck --sale=<id> recomputes tax and compares it with the stored snapshot.
  6. Who did it? audit_log where entity_id=<saleId> shows the cashier, any approver, the device and overrides.

Runbooks

RB-01 · A register isn't syncing
  1. Support console: last heartbeat. No heartbeat means a network or app problem in the shop. Ask the shop to open the register's status screen (it shows the connection test result).
  2. Heartbeat present but push failing: check last_error. A 401/403 means the device or user was locked, or the token was revoked (check the audit log). A 426 means the app is too old, so trigger an update. A 5xx means a server problem (check the 5xx alert).
  3. Items BLOCKED: find the error code, fix the cause (often a bug, so ship a fix), then Requeue.
  4. Never delete outbox items. If a payload is truly corrupt, export it, attach it to a ticket and escalate.
RB-02 · Receipt printer not printing
  1. The register's status screen has a Test print button. It shows the device bridge error (not found, offline, paper out).
  2. USB: check that the Windows driver isn't holding the port exclusively (the raw USB/serial mode is documented per model). LAN: ping the printer IP from the status screen, and check the port is 9100.
  3. Sinhala/Tamil text garbled: the printer must be in raster-image mode for those receipts (setting per printer profile).
  4. Selling continues without a printer. Receipts can be reprinted later from sales history.
RB-03 · Many NEGATIVE_STOCK exceptions
  1. Usually goods were sold before the goods receipt was posted. Check for unposted GRNs at that branch.
  2. Otherwise, barcodes may be mapped to the wrong SKU or unit (box vs piece). Check the most frequent SKUs.
  3. Resolve by posting the GRN or doing a stock count. Close the exceptions with a note.
RB-04 · RECEIPT_COLLISION on a register
  1. The register is locked automatically. Find out why the sequence repeated (restored backup, cloned PC image).
  2. Both sales are kept as facts. Mark one as the duplicate-number case in the exception note, for the tax auditor.
  3. Reset the register's sequence to the server's last sequence + 1 (two-person approval), then unlock.
RB-05 · Restore the database
  1. Declare an incident. Put the API in maintenance mode: registers keep selling, and pushes get 503 and retry.
  2. Restore to a new instance at the chosen point in time (managed PITR, or wal-g backup-fetch + recovery target).
  3. Run checks: ledger check, audit chain check, row counts vs. metrics from before the incident.
  4. Point the app at the new instance and leave maintenance mode. Registers re-push everything after the restore point, and idempotency makes this safe.
  5. Keep the old instance for 7 days for forensics. Write the post-mortem.
RB-06 · Roll back a bad release
  1. Backend: redeploy the previous image tag. Migrations are expand-only, so the old code works on the new schema.
  2. Register: stop the rollout ring (CDN channel file or Play staged rollout). Push the previous version to the affected ring as a "new" build if needed.
  3. Turn off the feature flag if the problem is behind one. That's the fastest fix.
RB-07 · Suspected account or device compromise
  1. Lock the user (bumps ver, tokens die within 10 minutes, refresh tokens are revoked at once) and lock the device.
  2. Review the audit log for that actor for the last 30 days: refunds, discounts, voids, exports, permission changes.
  3. Rotate any shared secret they could have seen. Tell the shop owner.
  4. Follow Incident response if more than one tenant may be affected.
RB-08 · Onboard a new shop
  1. Create the tenant (plan, modules), owner user, MFA setup link.
  2. The owner runs the onboarding wizard: business details, VAT number, branches, registers, tax settings, receipt layout.
  3. Import products from the Excel template. Fix errors from the preview report.
  4. Install the register app, enroll each device with a code, test print, test drawer, test scanner (including a GS1 2D code).
  5. Training sale on a training-mode register (sales are flagged and excluded from reports), then go live.
RB-09 · A shop leaves (offboarding)
  1. Export all their data (CSV/XLSX + tax documents PDF) and deliver it through a signed link.
  2. Suspend the tenant. Registers stop at the next pull.
  3. After the contract retention period, anonymise personal data. Tax facts are kept for the legal period, then deleted with their partitions.
