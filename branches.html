Branches & naming

RetailOS is trunk-based: main is the one long-lived branch and is always deployable. Every change is made on a short branch, reviewed in a pull request, and squash-merged back into main within a few days. There is no develop branch.

The branch model

Why there is no develop branch Staging already runs main, so develop would only be a second copy of it. Two long-lived branches drift apart, double the merges and hide integration problems until release day. With one engineer and CI checking every pull request, merging small changes into main often is safer. Unfinished features stay hidden behind a feature flag instead of on a branch.

Branch name format

<type>/<module>/<ticket>-<short-name>

feat/iam/AUTN-09-refresh-rotation
fix/sales/GH-142-receipt-gap
PartWhat it isRules
typeWhat kind of changeOne of the types below. Lowercase.
moduleWhere most of the change isOne of the module names below. If a change touches several modules, use the one with most of the work.
ticketWhy the change existsA build order task ID (AUTN-09) for planned work, or GH- and the GitHub issue number (GH-142) for bugs and pilot feedback. Uppercase. Required for feat, fix, hotfix, refactor and perf; optional for docs, test, chore and ci.
short-nameA reminder of the changeLowercase words joined with hyphens, 2–6 words. Letters, digits and hyphens only. The whole branch name stays under 60 characters.

The check in CI

A pull request fails if its branch name doesn't match this pattern (build order task SET-15):

^(feat|fix|hotfix|refactor|perf)/[a-z0-9-]+/([A-Z][A-Z0-9]{0,4}-\d{2}|GH-\d+)-[a-z0-9]+(-[a-z0-9]+){1,5}$
^(docs|test|chore|ci)/[a-z0-9-]+/(([A-Z][A-Z0-9]{0,4}-\d{2}|GH-\d+)-)?[a-z0-9]+(-[a-z0-9]+){1,5}$
^release/(backend|admin|register)-\d+\.\d+$

The same script also rejects names longer than 60 characters. It can run locally as a Git pre-push hook too, so a wrong name is caught before pushing.

Commits and pull requests follow the branch

BranchPull request title (the squash commit on main)
feat/iam/AUTN-09-refresh-rotationfeat(iam): rotate refresh tokens on every use (AUTN-09)
fix/sales/GH-142-receipt-gapfix(sales): no gap in receipt numbers after a crash (GH-142)
  • The pull request title uses the same type and module, says what changed in plain words, and ends with the ticket. It becomes the one commit on main and the line in the release notes.
  • For a GitHub issue, the description says Closes #142 so the issue closes when the pull request merges.
  • Commits on the branch can be small and informal; only the squash commit lands on main.

A branch from start to finish

  1. Start from an up-to-date main: git switch main && git pull, then git switch -c feat/iam/AUTN-09-refresh-rotation.
  2. Push early and open a draft pull request, so CI runs from the first push.
  3. Keep up with main: if main moved on, rebase (git pull --rebase origin main) or press "Update branch" on the pull request.
  4. Mark it ready when the task is done, the checks are green and the definition of done is met.
  5. Squash merge. GitHub deletes the branch; delete it locally too.
  6. Tick the task in the build order, and set the endpoint status in tools/build_endpoints.py if it added an endpoint.

A branch older than three days is a warning sign. Split the work, merge what's ready behind a feature flag, and continue on a new branch.

SituationWhat to do

The bug is in an older version still used by shops (registers lag one version, INV-13)Fix it on main first. Then create release/register-1.6 from the tag register-v1.6.0 if it doesn't exist, cherry-pick the fix onto it in a pull request, and tag register-v1.6.1 from the release branch.
The code no longer exists on mainFix it on the release branch only, and say so in the pull request.
