RetailOS system design

RetailOS is DevCity's point-of-sale and back-office platform for general retail, pharmacies and grocery stores. Registers keep selling when the internet drops, stock is tracked per batch and expiry date, and invoices follow Sri Lankan VAT rules. One cloud backend serves every shop and branch.

At a glance

Modular monolith

One Spring Boot app with strict module boundaries. Split a module out only when measurements demand it.

Offline-first

Every register sells from its own SQLite database and syncs in the background. A sale is never lost and never rejected.

1 UI, 2 shells

One React register app packaged for Windows (Electron) and Android (Capacitor), with a device bridge for printers, drawers and scanners.

Core + extensions

The core understands a generic sale. Pharmacy and grocery plug in as extension modules. General retail is the core alone.

Cloud-agnostic

A container, PostgreSQL and S3-compatible storage. It runs on any provider from about US$20 a month at pilot scale.

Tax-ready

A Tax module owns invoice numbering and credit notes, with an adapter for IRD e-invoicing and secured POS rules.

Invariants (rules that must never break)

Rules are numbered INV-nn and cited across all pages, in code comments and in tests. If code breaks an invariant, the code is wrong. The full list is in Guide for AI agents. The most important ones:

IDRule
INV-01Every tenant-owned row has tenant_id, and every request runs with RLS bound to that tenant.
INV-02A completed sale is a fact. It is never rejected, updated or deleted, and corrections are new linked records.
INV-03Money is decimal everywhere: NUMERIC(19,4) in the database and a string in JSON. Never use floats.
INV-04Stock changes only through stock_movement rows. Balances are a rebuildable projection.
INV-05Every write from a register carries a client UUID that acts as an idempotency key.
INV-08Modules communicate only through public APIs and events, and never read each other's tables.

Assumptions and constraints

  • Market: Sri Lanka first. Prices are in LKR, the time zone is Asia/Colombo, and the UI is in English, Sinhala and Tamil.
  • Team: one engineer at the start. Scope and technology are picked so one person can build, deploy and support the system with AI assistance. A second engineer is recommended before the pilot (see Roadmap).
  • Customers: small and medium shops with 1 to 20 branches and 1 to 10 registers per branch, in general retail, pharmacy and grocery.
  • Counter hardware: Windows PCs, Android tablets and Android phones, all in the MVP from the same codebase (ADR-003).
  • Cloud: no provider chosen yet. The design uses only portable building blocks (see Cost & scaling).
  • Commercial model: proposed in Plans: four plans (Lite for mobile, Starter, Business, Enterprise), a monthly subscription per branch, and paid industry modules. Still open question Q-05 until the pilot confirms it.
