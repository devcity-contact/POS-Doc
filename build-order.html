Build order

Every MVP task, from an empty repository to launch, in the order to build it: 350 tasks (232 backend, 48 admin web, 36 register app, 34 Try it checks) in 53 categories and eight stages. Tick each one when it is built, so everyone can see what is done and what comes next.

The approach

  1. Project setup first (stage 1): both builds, CI, the app shells, shared building blocks and a staging server, proven by a walking skeleton.
  2. Then the whole database (stage 2): all 56 tables in four migrations with row-level security, plus the test tools (database build order).
  3. Then features, area by area, in the order of the four database areas: store & staff (stage 3), catalog (stage 4), inventory (stage 5) and sales (stages 6 and 7). Stage 8 is the pilot and launch.
  4. Each feature is a vertical slice: the backend API with its tests, then the admin or register screen connected to it, then it runs on staging. Each stage ends with a Try it list: steps someone who didn't build it can follow on staging. The phase exit tests from the roadmap are part of these lists.
How to use this page
  • Done means: merged to main with tests, CI green, the screen works against the real API on staging, and the definition of done is met.
  • Your ticks are saved in this browser only. To share progress, use Copy built IDs and paste the result over DONE in tools/build_order.py, then regenerate and commit. Those tasks then show as built for everyone (locked tick). Export and Import move your own ticks between browsers.
  • Use Part to split the work: a backend developer filters to Backend, a front-end developer to Admin web or Register app. Inside a stage, the front-end can start a screen against the prototype while its API is being built.
  • IDs never change. Quote them in branch names, commits and pull requests, e.g. feat/AUTN-09-refresh-rotation. Screen codes (A-21, R-04) match the MVP screen list.

    Shared building blocks Backend P0

    0 / 14

    Used by every module. Build them once, before any feature, so the same bug doesn't appear in fifteen places. (Smaller blocks such as rate limiting and file storage are built later, with the first feature that needs them.)

    1. Value objects on BigDecimal (scale 4 and 3) with fixed rounding rules; UUIDv7 id generator (INV-03). → Data model › conventions
    2. BigDecimal written as a string with 4 decimals (INV-03), ISO-8601 UTC times, strict unknown-field policy for commands. → API › conventions
    3. Injectable Clock; business_date from the branch time zone (Asia/Colombo). Store UTC timestamptz (INV-15). → Offline & sync › clocks and dates
    4. RFC 9457 Problem Details with a stable code, requestId, localised detail; never a stack trace or SQL. → API › error format · Modules › error code catalog
    5. Bean Validation on request bodies → VAL-001 with a list of field errors. → API › error format
    6. ?limit=50&cursor=… returns nextCursor. Shared parsing for from, to, branchId, sort. → API › conventions
    7. ETag from version; PUT/PATCH require If-Match; a mismatch returns 412. → API › conventions
    8. Read X-Request-Id, traceparent, X-App-Version, X-Device-Id; tenant, user, device and request id in the log context. → API › standard headers
    9. JSON logs. Phone numbers, e-mails, tokens and PINs are masked or never logged. → Security › encryption and secrets
    10. springdoc groups for /api/v1 and /sync/v1; Swagger UI only in local and staging. → API › openapi and client generation
    11. CI generates packages/api-client from OpenAPI and fails on a breaking change (INV-13). Money stays a string. → API › openapi and client generation
    12. Spring Modulith event publication registry, idempotent listener pattern, incomplete events retried on start (ADR-007). → Modules › domain event catalog
    13. Scheduler with ShedLock and a tenant-aware job runner that sets the tenant before touching data. → Tech stack

    Stage 2 · Database, migrations and test base P0–P1

    Create all 56 tables in four migrations, in area order, with row-level security, plus the test tools every feature will use. Until the pilot, V1–V4 are a draft: edit them in place and rebuild the database when a feature shows the design was wrong. From the pilot on, only add new migrations.

    Database and migrations Backend P0

    0 / 12

    The order follows the four areas in the database build order.

    5. V2__catalog.sql: brand, category, tax rate, product, unit, SKU, unit conversion, barcode, price lists, discount rules. → Data model › build order
    6. V3__inventory.sql: suppliers, goods receipts, locations, batches, stock balance, stock movement, counts, stock exceptions. → Data model › build order
    7. V4__sales.sql: sale, lines, allocations, returns, payments, tender types, tax documents, fiscal submissions, customers, credit, held bills, receipt registry (unique register + seq, INV-06). → Data model › build order · receipt_registry

    9. Grants or triggers stop UPDATE/DELETE on sales, lines, payments, stock movements, credit ledger and audit log (INV-02, INV-04, INV-09). → Data model › conventions

    Tenancy and isolation Backend P1

    0 / 6

    One business can never see another's data.

    1. The tenant comes only from the signed token (tid), never from a URL or body. → Security › tenant isolation
    2. set_config('app.tenant_id', …, true) at the start of every transaction, for JPA and JdbcClient (INV-01). → Security › tenant isolation
    3. Jobs and listeners set the tenant explicitly; cache keys and job payloads include the tenant id. → Security › tenant isolation
    4. Suspended tenant → TEN-001. Check tenant_module before industry features. → tenant_module
    5. Users scoped to branches through user_role.branch_id; a manager of branch A can't act in branch B. → Security › authorisation and permission matrix
    6. Every repository and REST endpoint called with another tenant's token returns nothing or 403. Grows with every new endpoint. → Security › tenant isolation

    Authentication Backend P1

    0 / 17

    Web sign-in with password and two-step, staff PIN on registers, and tokens.

    1. m=64 MB, t=3, p=1; re-hash on login when settings change. → Security › authentication
    2. At least 10 characters, checked against a breached-password list, no forced rotation. → Security › authentication
    3. EdDSA or ES256 with kid; JWKS publishes the current and previous key; rotation every 90 days. → Security › tokens and sessions
    4. 10-minute JWT with sub, tid, bid, did, roles, ver. → Security › tokens and sessions
    5. Nimbus JWT validation, claims → current user, AUTH-001 for a missing or expired token. → Security › tokens and sessions
    6. Bucket4j: login, PIN, enroll and refresh 10 per minute then lockout; admin 300 per minute per user; 429 with Retry-After. Sync limits are added in later stages. → API › rate limits
    7. POST /api/v1/auth/login: e-mail + password (+ TOTP). Same error for a wrong e-mail or password; failures locked out and audited. → API › auth and devices
    8. Set up with a QR code and a confirm code, recovery codes, required for OWNER and ADMIN. → Security › authentication
    9. Opaque, stored hashed, 30-day sliding life, rotated on every use; reuse revokes the family. POST /auth/refresh. → Security › tokens and sessions · refresh_token
    10. Refresh token in an HttpOnly; Secure; SameSite=Strict cookie scoped to /api/v1/auth. → Security › tokens and sessions
    11. POST /auth/logout revokes the refresh-token family. → API › auth and devices
    12. A permission change or deactivation increments ver; older tokens are rejected. → Security › tokens and sessions
    13. Mail port: Mailpit locally, a provider in production; templates in en/si/ta. → Tech stack
    14. Single-use, short-lived e-mail link; signs out all sessions. → Security › authentication
    15. E-mail invitation → set password → set up two-step if the role needs it. → Security › authentication
    16. Set and reset a 4–6 digit PIN; POST /api/v1/auth/pin on an enrolled device; 5 failures → 5-minute lockout on that device, audited. → Security › authentication · API › auth and devices
    17. Login, two-step, refresh rotation and reuse detection, lockouts, expired and tampered tokens. → Developer guide › testing
