Offline & sync

Every sale follows the same path whether the network is up or down. The register sells from its own database, then a background engine pulls reference data and pushes facts. This is the largest technical risk in the product, so this page defines the protocol exactly.

The three rules that make sync safe
  1. Facts come from the register, reference data from the server (INV-12). The server never rejects a completed sale (INV-02).
  2. Every fact has a client-generated UUID, and pushing it twice is harmless (INV-05).
  3. Receipt numbers are allocated locally, gap-free, per register (INV-06).

Enrolling and bootstrapping a register

  1. A manager creates the register in the admin app and gets a one-time enrollment code, valid for 15 minutes.
  2. The register app generates a device key pair, held by Windows DPAPI or the Android Keystore, and calls POST /api/v1/devices/enroll with the code and its public key. It receives a device ID and device credentials.
  3. The register downloads the latest catalog snapshot: a gzipped NDJSON file per scope, built nightly per tenant and branch, stored in object storage and fetched with a short-lived signed URL. It loads the snapshot into SQLite.
  4. It then pulls changes since the snapshot's cursor (delta).
  5. The server tells it the next receipt sequence: 1 for a new register, or the last known sequence + 1 for a replaced device on an existing register.
  6. The register is ready once staff can sign in with a PIN and a test receipt prints.

Pull: the change feed

200 OK
{
  "cursor": 185220,
  "hasMore": true,
  "changes": [
    { "seq": 184221, "scope": "prices", "entity": "price_list_item", "op": "UPSERT",
      "id": "0190f3...", "data": { "skuId": "...", "unitId": "...", "price": "320.0000", "validFrom": "2026-11-20T00:00:00Z" } },
    { "seq": 184222, "scope": "catalog", "entity": "barcode", "op": "DELETE", "id": "0190aa..." }
  ]
}
  • The register applies each page in one local transaction and stores the new cursor in the same transaction, so a crash in the middle is safe.
  • Changes are filtered on the server by tenant, by branch (when branch_id is set) and by enabled modules.
  • staff and settings scopes are pulled first and more often (every 60 s while online), so a blocked user or a recalled batch takes effect quickly. The settings scope also carries the shop's plan features and status, so an offline register hides what the plan doesn't include and, once the shop is locked for late payment, won't open a new shift (Plans).
  • If the cursor is older than the compaction window (30 days), the server returns 409 SYNC-003 and the register downloads a fresh snapshot.
  • Responses are gzip-compressed. A typical delta is a few KB. This keeps mobile-data and cloud egress costs low.

Push: sending facts

POST /sync/v1/push
{
  "registerId": "0190f3c2-...",
  "items": [
    { "kind": "CASH_SESSION_OPENED", "id": "0191a0...", "payload": { ... } },
    { "kind": "SALE", "id": "0191a1...", "payload": {
        "receiptNo": "CMB01-R02-000154", "receiptSeq": 154,
        "cashSessionId": "0191a0...", "completedAt": "2026-11-19T04:12:09.120Z",
        "deviceSeq": 9123, "priceListId": "...",
        "lines": [ { "id": "...", "skuId": "...", "qty": "2.000", "unitId": "...",
                     "unitPrice": "320.0000", "discount": "0", "taxRate": "18.0000",
                     "taxAmount": "97.6271", "lineTotal": "640.0000", "batchHint": null } ],
        "payments": [ { "id": "...", "tender": "CASH", "amount": "1000.0000" } ],
        "change": "360.0000", "grandTotal": "640.0000" } }
  ]
}

200 OK
{ "results": [
  { "id": "0191a0...", "status": "ACCEPTED" },
  { "id": "0191a1...", "status": "ACCEPTED_WITH_EXCEPTION",
    "exceptions": [ { "code": "NEGATIVE_STOCK", "skuId": "...", "onHand": "-1.000" } ] }
] }
  • Order matters. Items are pushed in local creation order (deviceSeq), so a cash session is opened before its sales and a sale is recorded before its return.
  • Each item is its own server transaction. One bad item doesn't block the rest. If an item fails because something it depends on is missing, that item is retried. Items for other cash sessions are not held back.
  • Idempotency. The server first checks sync_inbox. If the ID exists, it returns the stored result with status DUPLICATE. The inbox row and the sale are written in the same transaction.
  • Retry policy. Exponential backoff (2 s, 4 s, 8 s … capped at 5 min) with jitter, so 300 registers coming back online after an outage don't all hit the server at once.
  • Batch size. Up to 50 items or 512 KB per request.

Receipt numbering

Format: {branchCode}-{registerCode}-{seq:6}, e.g. CMB01-R02-000154. Tax invoices use their own series, e.g. CMB01-R02-TI-000031.

  • The sequence is incremented inside the same local transaction that completes the sale, so there are no gaps and no duplicates on that register.
  • Each register has its own sequence, so registers never coordinate with each other, online or offline.
  • Voided open sales never get a number. Only completed sales do.
  • Receipt collision. If the server receives the same (register, seq) with a different sale ID (for example after a register was restored from an old backup), it records both, raises RECEIPT_COLLISION, locks the register and tells support. The register must re-sync its sequence from the server before it sells again.

Offline guard rails

SituationRegister behaviour
Offline for more than 24 h (configurable)A yellow banner says prices may be out of date. Selling continues.
Offline for more than 72 h (configurable)A red banner. A manager PIN is needed each day to continue (limits the risk from a stolen device).
Credit sale offlineChecks the last synced balance plus this register's unsynced credit sales. Going over the limit needs a manager override.
Loyalty redemption offline R2Capped per customer per day, so points can't be double-spent on two registers.
Stock shown offlineLast pulled balance minus local unsynced sales. Shown as an estimate, never used to block a sale.
Expired batch, data staleWarns and asks for confirmation. The server raises EXPIRED_BATCH_SOLD (BR-09).
Returns of sales from another registerOnline: looked up on the server. Offline: allowed with a manager PIN, using the receipt barcode data. Checked by the server on push.
Recalled or blocked batchBlocked as soon as the high-priority pull arrives. Earlier sales are reported.

Clocks and dates

  • The register sends completedAt (device clock) and a monotonic deviceSeq. The server adds received_at.
  • Every sync response includes the server time. If the device clock is off by more than 5 minutes, the register warns, and the server tags pushed sales with a CLOCK_SKEW exception.
  • business_date is taken from the cash session's opening date in the branch time zone, so a shift that runs past midnight stays on one business day.

Several registers in one branch

Registers don't talk to each other. Each one sees other registers' sales through the server after both have synced, usually within a minute while online. During a long internet outage, stock estimates on each register drift apart. This is acceptable because sales are never blocked on stock. Peer-to-peer sync over the shop's local network is a possible later enhancement (Later), needed mainly by the restaurant module.
