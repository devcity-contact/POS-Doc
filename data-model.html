Data model

PostgreSQL is the system of record for every tenant. The model has four areas: organisation, catalog and pricing, inventory and purchasing, and sales and money. Fact tables are append-only. Balances are projections that can be rebuilt.

The diagram is generated by tools/build_db_map.py, so update the script when a table changes. Each table is explained one by one in the data dictionary.

Build order: database first, then features

The plan for RetailOS is to create the database for all four areas first, then build the features area by area in the same order. The order follows the dependencies: every later area points back to the earlier ones, never forward.

Rules for building the database first
  • It is a draft until the pilot. Before the first real shop, edit the migrations freely and rebuild development databases. After the first production install, migrations only add and stay compatible with the previous register version (INV-13): never rename or remove a column in one step.
  • Security goes in with each table, not later. Every migration adds tenant_id, its indexes and the row-level security policy (INV-01). The tenant-isolation test runs from step 1.
  • Facts are append-only from day one. The application role gets no UPDATE or DELETE rights on sale, sale_line, stock_movement and audit_log (INV-02, INV-04, INV-09).
  • Partition the big tables at creation. sale, sale_line and stock_movement are partitioned by month from the first migration, because partitioning a filled table later is slow (see partitioning).
  • Only add constraints you are sure of. Keys, NOT NULL, CHECK lists and the unique barcode per tenant go in now. Columns for features that come later stay nullable.
  • Report views are not tables. The mv_* materialized views are created when the reports are built, once real data shows what the reports need.
  • The register's SQLite schema follows the same order (see register local schema), but only for the tables the register needs offline.

Conventions

TopicRule
Primary keysuuid, version 7 (time-ordered, so indexes stay compact). Created by the server with uuidv7(), or by the register for facts it creates (INV-05).
TenantEvery tenant-owned table has tenant_id uuid not null as the first column of its composite indexes, plus an RLS policy (INV-01).
Moneynumeric(19,4). Currency is the tenant's (LKR) and is stored on documents for the future (INV-03).
Quantitynumeric(14,3), which allows weights in kg to 3 decimal places.
Timetimestamptz in UTC. business_date date is calculated in the branch's time zone for daily reports (INV-15).
Audit columnscreated_at, created_by, updated_at, updated_by, version on mutable tables (optimistic locking). Facts have only created_*.
Soft deleteMaster data uses archived_at. Facts are never deleted.
Namingsnake_case, singular table names, extension prefixes ph_, gr_.
Enumstext with a CHECK constraint. They are easier to evolve than PostgreSQL enum types.
Flexible extrasOne attributes jsonb on product and customer, for display-only data.

  register_id      uuid not null references register(id),

  customer_id      uuid references customer(id),
  receipt_no       text not null,                 -- {branch}-{register}-{seq} (INV-06)
  receipt_seq      bigint not null,
  status           text not null check (status in ('OPEN','COMPLETED','VOIDED')),
  price_list_id    uuid not null,

  discount_total   numeric(19,4) not null default 0,
  tax_total        numeric(19,4) not null,
  rounding         numeric(19,4) not null default 0,
  grand_total      numeric(19,4) not null,

  attributes       jsonb not null default '{}',
  primary key (id, business_date)                 -- partition key must be part of the PK

-- Ordered change feed that registers pull from (see Offline & sync)
create table sync_change_log (
  seq          bigint generated always as identity primary key,
  tenant_id    uuid not null,
  branch_id    uuid,                -- null = all branches of tenant

Row-level security

Tenant isolation is enforced twice. Every repository filters by tenant_id, and PostgreSQL RLS blocks any row of another tenant even when a query forgets the filter.

alter table sale enable row level security;
alter table sale force row level security;

create policy tenant_isolation on sale
  using (tenant_id = current_setting('app.tenant_id')::uuid)
  with check (tenant_id = current_setting('app.tenant_id')::uuid);

-- The backend sets the tenant at the start of EVERY transaction (pooled connections):
select set_config('app.tenant_id', :tenantId, true);   -- true = local to transaction
  • The application connects as retailos_app, which is not the table owner and has no BYPASSRLS.
  • Migrations run as retailos_migrator (the owner). Platform jobs that must see every tenant use retailos_platform, only inside the worker, with every use logged.
  • If app.tenant_id is not set, current_setting raises an error, so the query fails closed.
  • CI test TenantIsolationIT creates two tenants and asserts that every repository returns zero rows across tenants (NFR-09).

Retention. Sales, tax and audit partitions are kept online for 2 years, then detached and exported to compressed files in cold object storage. They are kept for the statutory period (NFR-14) and can be restored on request.
