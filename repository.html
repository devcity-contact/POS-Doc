Repository & GitHub

All RetailOS code lives in one private GitHub repository: the backend, the admin web app, the register app with its Windows and Android shells, the shared packages and the infrastructure scripts. This page explains why, how the folders fit together, and how a change travels from a branch to the shops.

The repository at a glance

Why one repository

  • Most changes cross boundaries. A new field on a sale touches a migration, the backend API, the generated client, the register and an admin screen. In one repository that is one pull request, tested together. Across repositories it is several pull requests that must be merged in the right order.
  • Shared code stays simple. register-core, ui, i18n and api-client are used by more than one app. In one repository they are workspace folders; across repositories each would need publishing and version bumps.
  • Java and TypeScript check the same cases. shared/test-vectors drives both test suites (ADR-012), which only works when both live together.
  • Windows and Android are not two apps. They are one React register app in two thin shells (ADR-003). Splitting them would copy the UI.
  • One engineer, one pipeline. One set of settings, secrets and CI to look after.
When to split a repository Only when a separate team owns a part and releases it on its own schedule, and the shared code between them has settled. That is not expected before Release 3. Until then, ownership is handled with a CODEOWNERS file inside the one repository.

CI builds only what changed

GitHub Actions uses path filters, so a backend change doesn't rebuild the Android app and a docs fix doesn't run the database tests. The scripts live in infra/ci/ so they can move to another CI if needed.

Versions and release tags

The backend, the admin app and the register ship on different schedules, so each has its own version and tag. Both register shells always share one version.

TagBuildsGoes to
backend-v1.4.0Docker imageProduction after a manual approval; health-gated, with a rollback plan
admin-v1.3.0Static siteCDN
register-v1.6.0Signed Windows installer and signed AAB/APKWindows auto-update and Google Play (or MDM), both with a staged roll-out
  • Versions follow semantic versioning. A register version must keep working with the backend for one version back (INV-13), so the backend never removes something an older register still uses.
  • Installers, APKs and AABs are attached to the GitHub Release for the tag, never committed to the repository.
  • Database migrations ship with the backend version and run before it starts (deployment).

Day-to-day commands

# start a task from the build order
git switch main && git pull
git switch -c feat/AUTN-09-refresh-rotation

# commit in small steps
git commit -m "feat(iam): rotate refresh tokens on every use"

# open the pull request
git push -u origin HEAD
gh pr create --fill

# after the squash merge
git switch main && git pull && git branch -d feat/AUTN-09-refresh-rotation

# release the register when staging is good
git tag register-v1.6.0 && git push origin register-v1.6.0

Open decision: where the docs live
