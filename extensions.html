Industry extensions

The core POS understands a generic sale. Industry modules add workflows and data through a small set of named extension points. A tenant switches modules on, and the core never imports an extension.

What is core and what is an extension

Several features that look industry-specific are needed by more than one industry, so they belong in the core.

Design the core for later extensions now, even though they ship later The core sale must support the states OPEN → COMPLETED (plus VOIDED before completion), service items, line options and a per-line staff member from the first migration. Adding these after launch would be a disruptive migration on the busiest tables.

How extensions plug in

Server extension points (SPI)

Each SPI is a Java interface in the core module's spi package. Extensions implement it as a Spring bean annotated with the module key. The core asks ExtensionRegistry for implementations enabled for the current tenant.

// sales/spi/SaleLineValidator.java
public interface SaleLineValidator {
    /** Industry module key, e.g. "pharmacy". Used to enable per tenant. */
    String moduleKey();

    /** Return warnings only. Never throw: a completed sale is a fact (INV-02). */
    List<SaleWarning> validate(SaleDraft sale, SaleLineDraft line, ValidationContext ctx);
}

// ext/pharmacy/internal/PrescriptionRequiredValidator.java
@Component
@ExtensionFor("pharmacy")
class PrescriptionRequiredValidator implements SaleLineValidator {
    public String moduleKey() { return "pharmacy"; }
    public List<SaleWarning> validate(SaleDraft s, SaleLineDraft l, ValidationContext c) {
        var info = drugInfo.find(l.skuId());
        if (info.isPresent() && info.get().prescriptionRequired() && !s.hasPrescriptionFor(l))
            return List.of(SaleWarning.of("PH-001", "Prescription missing for " + info.get().name()));
        return List.of();
    }
}

Register plugins

Register plugins are bundled into the app at build time, not downloaded at runtime: that is safer and works offline. They are activated by the tenant's enabled modules.

// packages/register-core/src/extensions/types.ts
export interface RegisterPlugin {
  key: 'pharmacy' | 'grocery' | string;
  lineValidators?: LineValidator[];          // mirror of server SaleLineValidator
  pricingRules?: PricingRule[];              // same rule logic as server, shared test vectors
  barcodeParsers?: BarcodeParser[];
  slots?: Partial<Record<SlotName, React.ComponentType<SlotProps>>>;
  migrations?: LocalMigration[];             // extension-owned local tables (ph_*, gr_*)
}

export type SlotName =
  | 'checkout.lineBadge' | 'checkout.beforeComplete' | 'checkout.sidePanel'
  | 'product.details'    | 'receipt.footer'          | 'settings.section';

Data ownership rules

  • Extensions own tables with a prefix (ph_, gr_, rs_, sl_) and reference core rows by ID. Never add industry columns to core tables.
  • Core tables have one attributes jsonb column for display-only extras. Anything you filter, join or validate on gets a real column in an extension table.
  • Extension migrations live in the extension's own Flyway location (db/migration/ext/pharmacy) and always run, so the schema is the same for every tenant. Only the data is per tenant.
  • Sync sends extension data only to tenants that have the module enabled.
  • Extensions never compute tax or change stock directly (INV-04, INV-07). They call core APIs.

Restaurant module Later

  • Uses the core OPEN sale state as a running ticket: lines are added over time and the ticket is completed at payment.
  • rs_table, rs_floor, rs_ticket(sale_id, table_id, covers, server_id), rs_kot(id, ticket_id, station, status).
  • Kitchen tickets print over the shop's local network, from register to kitchen printer, with no cloud round trip, so it works offline.
  • Modifiers use core sale_line_option. Service charge is a core charge line taxed by the Tax module.
  • Split bill = several sales created from one ticket. Delivery-app orders arrive as OPEN sales through an integration adapter.

Salon module Later

  • sl_appointment(id, customer_id, staff_id, service_sku_id, starts_at, ends_at, status) and sl_staff_schedule.
  • Checking in an appointment creates an OPEN sale with SERVICE lines and staff_id set. Commission reports read those lines.
  • Online booking (later) is a separate public endpoint with rate limiting.

Checklist: adding a new industry module

  1. Write an ADR: what the module does and which existing SPIs it uses. If it needs a new SPI, justify it with at least one concrete use case.
  2. Create the ext.<key> package with internal/, its own Flyway location and a table prefix.
  3. Implement the SPIs and annotate them with @ExtensionFor("<key>").
  4. Add the register plugin in packages/ext-<key> with validators, rules, slots and local migrations.
  5. Register the module key in ModuleCatalog and add its sync scopes.
  6. Add i18n keys for en/si/ta.
  7. Tests: SPI unit tests, a Modulith boundary test, and an end-to-end checkout with the module on and off.
  8. Document it on this page and add its tables to Data model.
Don't build a plugin framework in advance Build the SPIs that the pharmacy and grocery modules actually need. Generalise only when a second module needs the same hook. A runtime plugin marketplace is not a goal.
