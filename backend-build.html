Backend build order

Every backend task for the MVP, from an empty repository to launch: 223 tasks in 29 categories and six stages. Build them in this order. Tick each one when it is built, so everyone can see what is done and what comes next.

How to use this page
  • Order: stages and categories follow the roadmap phases P0–P7. Inside a category, tasks are in build order. The database is built first, all four areas (database build order).
  • Done means: merged to main with tests, CI green, and the definition of done met. Exit tests at the end of a phase are tasks too.
  • Your ticks are saved in this browser only. To share progress, use Copy built IDs and paste the result over DONE in tools/build_backend_plan.py, then regenerate and commit. Those tasks then show as built for everyone (locked tick). Export and Import move your own ticks between browsers.
  • IDs never change. Quote them in branch names, commits and pull requests, e.g. feat/AUTN-08-refresh-rotation.

    Shared building blocks P0–P1

    0 / 19

    Used by every module. Getting these right once avoids the same bug in fifteen places.

    1. Value objects on BigDecimal (scale 4 and 3) with fixed rounding rules; UUIDv7 id generator (INV-03). → Data model › conventions
    2. BigDecimal written as a string with 4 decimals (INV-03), ISO-8601 UTC times, strict unknown-field policy for commands. → API › conventions
    3. Injectable Clock; business_date from the branch time zone (Asia/Colombo). Store UTC timestamptz (INV-15). → Offline & sync › clocks and dates
    4. RFC 9457 Problem Details with a stable code from the error catalog, requestId, localised detail, never a stack trace or SQL. → API › error format · Modules › error code catalog
    5. Bean Validation on request bodies → VAL-001 with a list of field errors. → API › error format
    6. ?limit=50&cursor=… returns nextCursor. Shared parsing for from, to, branchId, sort. No offset paging on large tables. → API › conventions
    7. Mutable resources return ETag from version. PUT/PATCH require If-Match; a mismatch returns 412. → API › conventions
    8. Every REST POST that creates money or stock records stores the key and its response; a retry returns the same response. → API › conventions
    9. Read X-Request-Id, traceparent, X-App-Version, X-Device-Id; put tenant, user, device and request id in the log context. → API › standard headers
    10. JSON logs. Phone numbers, e-mails, tokens and PINs are masked or never logged. → Security › encryption and secrets
    11. springdoc groups for /api/v1 and /sync/v1; Swagger UI only in local and staging; openapi.json saved by CI. → API › openapi and client generation
    12. CI generates the client into packages/ and fails on a breaking API change (INV-13). → API › openapi and client generation
    13. Registers below the minimum supported version get 426 DEV-004. → API › standard headers
    14. gzip/br responses over 1 KB; accept gzipped request bodies on sync push. → API › conventions
    15. Login, PIN, enroll, refresh 10/min then lockout; admin 300/min per user; sync pull 120/min and push 60/min per device; 429 with Retry-After. → API › rate limits
    16. S3 client behind a port; keys prefixed tenants/{tenantId}/; downloads by 5-minute signed URL after a permission check. → Security › tenant isolation
    17. Spring Modulith event publication registry, idempotent listener pattern, incomplete events retried on start (ADR-007). → Modules › domain event catalog
    18. Scheduler with ShedLock (one instance runs each job) and a tenant-aware job runner that sets the tenant before touching data. → Tech stack
    19. Mail port: Mailpit locally, a provider in production; templates in en/si/ta. → Tech stack

    Tenancy and isolation P1

    0 / 6

    One business can never see another's data. Proven by a test that runs on every pull request.

    1. The tenant comes only from the signed token (tid), never from a URL or body. → Security › tenant isolation
    2. set_config('app.tenant_id', …, true) at the start of every transaction, for both JPA and JdbcClient (INV-01). → Security › tenant isolation
    3. Jobs and listeners set the tenant explicitly; every cache key and job payload includes the tenant id. → Security › tenant isolation
    4. Suspended tenant → TEN-001. Check tenant_module before industry features. → tenant_module
    5. Users scoped to branches through user_role.branch_id; a manager of branch A can't act in branch B. → Security › authorisation and permission matrix
    6. Every repository and every REST endpoint called with another tenant's token returns nothing or 403. Runs in CI. (P1 exit test) → Security › tenant isolation · Roadmap › exit tests

    Authentication P1

    0 / 16

    Sign-in for the web admin (password + MFA), for staff on a register (PIN), and tokens.

    1. m=64 MB, t=3, p=1 via Spring Security and Bouncy Castle; re-hash on login when settings change. → Security › authentication
    2. At least 10 characters, checked against a breached-password list (NIST 800-63B), no forced rotation. → Security › authentication
    3. EdDSA or ES256 key pair with kid; JWKS publishes the current and previous key; rotation every 90 days. → Security › tokens and sessions
    4. 10-minute JWT with sub, tid, bid, did, roles, ver. → Security › tokens and sessions
    5. Nimbus JWT validation, claims → current user, AUTH-001 for a missing or expired token. → Security › tokens and sessions
    6. POST /api/v1/auth/login: e-mail + password (+ TOTP). Same error for wrong e-mail or password; failures counted, locked out and audited. → API › auth and devices
    7. Set up with a QR code and a confirm code, recovery codes, required for OWNER and ADMIN. → Security › authentication
    8. Opaque, stored hashed, 30-day sliding life, rotated on every use. Reuse of an old one revokes the whole family. POST /auth/refresh. → Security › tokens and sessions · refresh_token
    9. Refresh token in an HttpOnly; Secure; SameSite=Strict cookie scoped to /api/v1/auth. Access token kept in memory only. → Security › tokens and sessions
    10. POST /auth/logout revokes the refresh-token family. → API › auth and devices
    11. A permission change or deactivation increments ver; older tokens are rejected (small in-memory cache). → Security › tokens and sessions
    12. Set and reset a 4–6 digit PIN (Argon2id, per-user salt). POST /api/v1/auth/pin on an enrolled device. 5 failures → 5-minute lockout on that device, audited. → Security › authentication · API › auth and devices
    13. Staff PIN hashes and roles go to the register in the users sync scope, so staff can sign in offline. → Security › authentication · Offline & sync › who owns what
    14. Single-use, short-lived e-mail link; signs out all sessions. → Security › authentication
    15. E-mail invitation → set password → set up MFA if the role needs it. → Security › authentication
    16. Login, MFA, refresh rotation and reuse detection, lockouts, expired and tampered tokens. → Developer guide › testing
