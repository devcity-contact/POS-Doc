Security architecture

A POS handles money, stock, staff and customer data for many businesses at once. The two worst outcomes are one shop seeing another shop's data, and undetected manipulation of sales or cash. Every control below exists to prevent one of those, or to limit the damage if it happens.

Target OWASP ASVS 4.0 level 2 for the backend and admin web, OWASP MASVS L1 for the Android register, and Electron security guidelines for the Windows register. The card-payment design stays out of PCI-DSS scope.

Tokens and sessions

  • Access token: signed JWT (EdDSA or ES256), 10-minute lifetime. Claims: sub, tid (tenant), bid (branch), did (device), roles, ver. Kept in memory, never in localStorage.
  • Refresh token: opaque, stored hashed on the server, 30-day sliding lifetime, rotated on every use. If an old one is reused, the whole token family is revoked (theft detection).
  • Admin web: the refresh token is in an HttpOnly; Secure; SameSite=Strict cookie scoped to /api/v1/auth.
  • Signing keys rotate every 90 days. The JWKS publishes the current and previous key.
  • A permission change or user deactivation increments ver. Tokens with an older ver are rejected, checked against a small in-memory cache.

Tenant isolation

  1. Token: the tenant comes only from the signed token, never from a URL or body.
  2. Application: a request filter sets TenantContext, and repositories always filter by tenant_id.
  3. Database: set_config('app.tenant_id', …, true) per transaction, with forced RLS on every tenant table. A missing setting fails closed. See Data model → RLS.
  4. Storage: object keys are prefixed tenants/{tenantId}/…. Downloads use 5-minute signed URLs issued after a permission check.
  5. Caches and jobs: every cache key and job payload includes the tenant ID. Jobs set the tenant context before touching data.
  6. Tests: TenantIsolationIT runs in CI against every repository and every REST endpoint with a token from another tenant.

Encryption and secrets

  • In transit: TLS 1.2/1.3 everywhere, HSTS on the admin domain, TLS between the app and the database when they're on different hosts.
  • At rest: encrypted disks and volumes on the database and object storage (provider-managed keys are acceptable). Backups are encrypted with a separate key (age/GPG or the provider's KMS) before leaving the database host.
  • Field-level: customer phone and e-mail are stored plainly for search, but are masked in logs and exports unless the user has permission. Prescription images are encrypted per tenant.
  • Secrets: never in git. Injected as environment variables from the host's secret store (Docker secrets, cloud secret manager, or sops-encrypted files for a VPS). Rotated every 90 days or immediately after a staff change. CI uses short-lived OIDC credentials where the provider supports them.

Audit logging

The audit log answers "who did what, when, from which device, and who approved it". It is tamper-evident:

audit_log(seq, tenant_id, occurred_at, actor_id, approver_id, device_id, action,
          entity, entity_id, before jsonb, after jsonb, reason, prev_hash, hash)

hash = SHA-256(prev_hash || tenant_id || seq || occurred_at || actor_id || action || entity_id || after)
  • The app role has only INSERT and SELECT on audit_log (INV-09). A nightly job verifies the chain per tenant and alerts on a break.
  • Audited actions: login and failures, PIN overrides, voids, refunds, discounts above limit, price changes, no-sale drawer opens, stock adjustments, batch blocks, role and permission changes, device enrollment and lock, settings changes, data exports, support access.
  • Registers keep a local audit chain and push it. The server appends it to the tenant chain with the device ID.

Payments and PCI-DSS

Stay out of PCI scope (INV-11) Card numbers, CVV and track data never enter RetailOS: no screen, API, log or database ever sees them. In the MVP the card terminal runs standalone, and the cashier records the approval code and last 4 digits. In R3, semi-integrated terminals send us only the result (approved/declined, reference, masked PAN). LankaQR uses dynamic QR codes from the acquirer, and we store only the transaction reference.

Privacy and data protection

Sri Lanka's Personal Data Protection Act, No. 9 of 2022, applies to customer and staff data. RetailOS is the processor, and each shop is the controller for its customers. Confirm current obligations with legal counsel, because operational dates have been phased.

  • Minimise: only a name and phone number are needed for credit and loyalty. No national ID numbers unless a regulator requires them (for example for controlled drugs, Q-03).
  • Consent: marketing needs an explicit opt-in, stored with time and source (F-305).
  • Rights: export and erasure of a customer's personal data (F-1006). Erasure anonymises the customer but keeps sales and tax facts, which have their own legal retention.
  • Data residency: choose a hosting region near Sri Lanka (e.g. Mumbai or Singapore) and document it in the customer contract.
  • Agreements: a data processing agreement in the tenant terms, and a list of sub-processors (hosting, SMS, e-mail).

Incident response

  1. Detect: alerts for auth failure spikes, RLS errors, audit chain breaks, unusual exports, register tokens used from new countries.
  2. Contain: revoke tokens (bump user or tenant ver), lock devices, rotate secrets, disable affected integrations. Runbook RB-07.
  3. Assess: use the audit log and access logs to find which tenants and records were affected.
  4. Notify: affected shop owners within 72 hours, and regulators as the law requires.
  5. Recover and learn: fix, restore if needed, write a blameless post-mortem, and add a test or alert that would have caught it.

Security checklist for every pull request

  • New endpoint has @PreAuthorize with a specific permission, plus a test proving a cashier token is refused.
  • New table has tenant_id, an RLS policy and a row in TenantIsolationIT.
  • No secrets, tokens, PINs or personal data in logs, errors or analytics.
  • Money uses BigDecimal/decimal.js. Inputs are validated with limits (max quantity, max discount).
  • Audit entry added for any action on money, stock, permissions or settings.
  • New dependency checked for licence and maintenance status.
