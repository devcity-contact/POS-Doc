Deployment & CI/CD

The goal is boring, repeatable releases that one engineer can run on a Friday without fear. Everything is a container image or a signed installer, built by CI, and nothing is deployed from a laptop. The design doesn't depend on a specific cloud provider: the hosting choice can be made later and changed without code changes.

Configuration and secrets

One image runs everywhere; the environment is chosen by a Spring profile of the same name (SET-07). Each profile is a file next to the shared application.yml in backend/src/main/resources/. Without a profile the backend refuses to start, so it can never fall back to a setting meant for another environment.

Later tasks add their own variables here (storage keys, signing keys, mail). If any is missing, the backend stops before it starts anything and names them all:

java.lang.IllegalStateException: Missing environment variables: DB_URL, DB_USER, DB_PASSWORD, ADMIN_ORIGIN.
Set them on the host (secret store or .env file); they are never written into the application*.yml files.
  • Typed settings. RetailOS's own settings (retailos.*) are a validated record, RetailOsProperties in platform/config: the environment, the business time zone (default Asia/Colombo, INV-15) and the admin origins. A wrong value, such as an unknown time zone, stops start-up.
  • Secrets never in git. In every profile except local and test, a setting named like a password, secret, token or key must be a bare ${VARIABLE} with no default. SecretsInConfigTest fails the build otherwise. Where the variables come from on each host: Security › Encryption and secrets.

CI/CD pipeline

Keeping CI fast and cheap

  • Cache Gradle, pnpm and Docker layers. Run front-end jobs only when apps/ or packages/ change (path filters).
  • Run Testcontainers PostgreSQL once per test JVM with a template database per test class, not a container per test.
  • Build Windows installers only on release tags, not on every PR.
  • Target: PR pipeline under 10 minutes.

The backend container

# backend/Dockerfile  (multi-stage)
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY . .
RUN ./gradlew bootJar -x test --no-daemon

FROM eclipse-temurin:25-jre-alpine
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app
COPY --from=build /src/build/libs/retailos.jar app.jar
USER app
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+UseZGC -XX:+ExitOnOutOfMemoryError"
EXPOSE 8080
HEALTHCHECK CMD wget -qO- http://localhost:8080/actuator/health/readiness || exit 1
ENTRYPOINT ["java","-jar","app.jar"]
  • One image for every environment. Behaviour comes from configuration: SPRING_PROFILES_ACTIVE=prod,api or prod,worker, or both in one process at Stage 1.
  • Configuration follows 12-factor rules: env vars for DB URL, bucket, JWT keys, SMTP and SMS. No configuration baked into the image.
  • Read-only root filesystem, non-root user, no shell needed in production.
  • Startup: Flyway migrates (only the instance holding the migration lock), then readiness turns green. Use Spring AOT/CDS to cut startup time and memory.

Zero-downtime deploys

  1. CI pushes the signed image retailos:1.6.0.
  2. The migration job runs expand-only migrations (new tables, nullable columns, new indexes created CONCURRENTLY). The old version keeps working.
  3. Rolling restart: start the new instance, wait for readiness, move traffic, drain the old one (graceful shutdown, 30 s). At Stage 1 with one instance, a short restart is fine because registers queue offline anyway.
  4. Smoke test: login, catalog pull, push one synthetic sale to the synthetic tenant.
  5. Contract migrations (drop old columns) ship in a later release, once no running code or supported register version uses them (INV-13).
  6. Rollback = redeploy the previous image. This is safe because migrations only expand.

Database migration rules

  • Flyway versioned scripts: V2026_11_19_1__add_batch_status.sql. Never edit a script once it's merged.
  • Every migration must be backward compatible with the previous app version (expand/contract).
  • Large backfills run as idempotent jobs in batches, not inside the migration.
  • Locks: set lock_timeout = '5s' in migrations. Create indexes CONCURRENTLY (in a non-transactional Flyway script).
  • Test every migration against a copy of a realistic-size dataset (synthetic, 10 million sale lines) before release.

Feature flags

Simple database-backed flags (feature_flag(key, scope global|tenant|register, enabled, rollout_pct)), synced to registers in the settings scope. Use them to ship unfinished code safely and to enable features for pilot shops first. Remove each flag within two releases of 100% rollout.

Versioning

  • Semantic versioning for backend, admin and register, with one shared version number per release train (e.g. 1.6.0), so support knows what goes with what.
  • A changelog is generated from Conventional Commits. Release notes in English, plus a short Sinhala/Tamil summary for shop staff.
