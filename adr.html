ADR-001 · Modular monolith with Spring Modulith

Context. One engineer, one database, and sales and stock must change together atomically. Microservices would add network failures, distributed transactions and operational cost with no benefit at this scale.

Decision. One Spring Boot application split into modules. Spring Modulith verifies dependencies in tests and provides the event publication registry.

Consequences. Simple deploys and real ACID transactions. Boundaries need discipline, which the CI test enforces. A module can be extracted later along its boundary.

Rejected. Microservices (too much operations work for the team size). A plain layered monolith without enforced boundaries (erodes within months).

Revisit when. One module needs independent scaling or release cadence, proven by metrics.

ADR-002 · Local-first register with SQLite

Context. Sri Lankan shops have unreliable internet and power. Competitors sell offline billing. The original blueprint deferred offline to V1.2, which would have forced a rewrite of checkout, numbering and stock rules.

Decision. The register always sells from a local encrypted SQLite database and syncs in the background. Online and offline use one code path.

Consequences. More register complexity (sync engine, local migrations) and some duplicated logic (see ADR-012). The server load is mostly ingestion, which is cheap. Stock on other registers is eventually consistent.

Rejected. An online thin client (till stops when the network drops). A PWA with IndexedDB (can't reliably hold the sale queue, open the cash drawer or print raw ESC/POS).

ADR-003 · One React register UI in Electron and Capacitor shells

Context. Counters use Windows PCs and Android tablets. The team is one engineer who knows React and TypeScript.

Decision. One React app and one pure-TypeScript domain package. Electron packages it for Windows and Capacitor for Android. Hardware is reached through a DeviceBridge port with an adapter per shell. Windows ships in the MVP and Android in R2.

Consequences. Electron installers are large (~100 MB) and use more RAM, which is acceptable on POS PCs with 4 GB. Two native adapter sets to maintain.

Rejected. Tauri 2 for both platforms (smaller, but device plugins need Rust, which adds a second language for a one-person team; worth revisiting later). Native apps per platform (double the UI work). Flutter (new language, weaker reuse with the React admin).

ADR-004 · Shared-schema multi-tenancy with row-level security

Context. Hundreds of small tenants, low cost per tenant, one team.

Decision. One database and schema. tenant_id on every tenant-owned table. PostgreSQL RLS forced on these tables, with the tenant set per transaction.

Consequences. Cheapest option, with simple migrations. A noisy tenant can affect others (mitigated with rate limits and, later, cells). RLS adds a little planning overhead, which is acceptable.

Rejected. Schema per tenant (migration time grows with tenant count). Database per tenant (too expensive for small shops).

ADR-005 · Stock as an append-only movement ledger with batch-level FEFO

Decision. All stock changes are stock_movement rows at batch level. stock_balance is a projection updated in the same transaction and checked nightly. Allocation is FEFO unless the cashier or a GS1 code names a batch.

Consequences. Every figure can be explained. Correct margins per batch. More rows (handled by partitioning). Rows are locked in batch-ID order to avoid deadlocks.

ADR-006 · Industry features as extension modules

Context. Retail, pharmacy and grocery now; restaurant and salon later. Putting industry logic in Sales would make the core unmaintainable.

Decision. The core understands a generic sale. Industry modules implement named SPIs (server) and register plugins with UI slots, own prefixed tables, and are enabled per tenant through tenant_module. Some shared capabilities (batches, service items, line options, open-order state) live in the core.

Consequences. A clean core, modules that can be sold as add-ons, and safe enablement per tenant. SPIs are designed from real cases, not up front.

ADR-007 · Transactional outbox via event publication registry, no broker

Decision. Domain events are stored in the same transaction (Spring Modulith event publication registry) and delivered to in-process listeners, with retries for incomplete publications. No Kafka or RabbitMQ.

Consequences. Reliable side effects with nothing extra to run. Listeners must be idempotent. If a service is extracted later, events can be externalised to a broker with Modulith's support.

ADR-008 · Stay out of PCI-DSS scope

Decision. Card data never enters RetailOS. MVP: standalone terminals, recording the approval reference only. R3: semi-integrated terminals that return only the result.

Consequences. No PCI audit cost. Slightly slower card flow in the MVP, because the cashier keys the amount into the terminal.

ADR-009 · Cloud-agnostic container hosting, no Kubernetes

Decision. One OCI image, PostgreSQL and S3-compatible storage. It runs on a VPS with Docker Compose at pilot stage, and on any managed container service later. Configuration via env vars, with an off-site backup at a second provider.

Consequences. The hosting decision can wait, and provider lock-in stays low. No proprietary queues or databases in the core path.

Revisit when. More than about 10 services or a team that already runs Kubernetes.

ADR-010 · Sales are never rejected; exceptions instead

Context. A sale made offline has already happened: the customer has left with the goods. The server can't undo it.

Decision. The server records every completed sale. Price mismatches, short stock, expired batches and clock skew become sale_exception rows for a manager to review. Strict stock blocking is an option for online registers only.

Consequences. Stock can go negative. An exception queue UI and alerts are needed.

ADR-011 · Register-generated UUIDv7 and per-register receipt sequences

Decision. Registers create IDs (UUIDv7) for every fact they create, and number receipts from their own gap-free sequence. The server enforces uniqueness through sync_inbox and receipt_registry.

Consequences. No coordination is needed between registers. Replacing a device needs a sequence hand-over. Restoring a register from an old backup is detected as a collision.

ADR-012 · Shared test vectors for logic duplicated in Java and TypeScript

Context. Pricing, tax, rounding, GS1 parsing and promotions run on the register (offline) and are checked on the server.

Decision. Keep the logic in both languages, but drive both test suites from the same JSON vectors in shared/test-vectors. A change to the rules means changing the vectors first.

Rejected. Running the backend logic in the register (a JVM on the device is too heavy). Compiling TypeScript into the JVM through GraalJS (too complex for now).

ADR-013 · Sinhala and Tamil receipts printed as raster images

Context. Most thermal printers don't have Sinhala or Tamil fonts, and complex script shaping isn't supported in ESC/POS text mode.

Decision. The register renders the receipt (or the non-Latin parts) to a 1-bit image with system fonts (Noto Sans Sinhala/Tamil) and sends it with the ESC/POS raster command. English-only receipts can use text mode, which is faster.

Consequences. Slightly slower printing. Fonts are bundled with the app.

ADR-014 · JPA for CRUD, explicit SQL for stock and reports

Decision. Spring Data JPA for master data and admin CRUD. JdbcClient with hand-written SQL for allocation, row locking, ledger checks and reports, where you need to see the exact query.

Consequences. Two data-access styles, kept apart by module and use case.
