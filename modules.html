Backend modules

Each module owns its tables, exposes one public API interface and publishes events. If you need data from another module, call its API or listen to its events. Never query its tables (INV-08).

Dependency rules

  • Allowed direction: extensions → core → platform. Platform never depends on core, and core never depends on an extension.
  • Core modules may call another core module's *Api interface only when they need an answer now (inside the same transaction). Everything else uses events.
  • Using another module's internal package, or circular dependencies, fail the build (ApplicationModules.of(RetailOsApplication.class).verify()). How the boundaries are set and checked: Module boundaries.
  • The Sales module owns the sale transaction. Stock deduction happens in the same database transaction through InventoryApi.allocateAndDeduct(), because money and stock must never drift apart. Events are only for work that can safely happen afterwards (customer stats, notifications, reporting).

Module details

Sales: records sales, returns and held bills

Responsibility. Turns a register's completed sale into a permanent fact, allocates batches, and records returns linked to original lines. Owns the sale lifecycle.

Public APISalesApi.recordSale(RecordSaleCommand), recordReturn(...), getSale(saleId), findByReceipt(receiptNo)
PublishesSaleCompleted, SaleReturned, SaleException (price mismatch, negative stock, expired batch)
ConsumesNone. It is called by Sync and by the REST API.
SPI (extension points)SaleLineValidator, SaleEnricher, ReceiptSectionProvider
InvariantsINV-02 INV-05 INV-06 INV-10 INV-14

Key logic. RecordSale: check idempotency (sale UUID) → validate tenant, branch, register and cash session → run SPI validators (they warn, they never reject) → call InventoryApi.allocateAndDeduct (locks batch rows in batch_id order) → persist sale, lines, allocations and payments → call TaxApi.issueDocument when needed → publish SaleCompleted through the outbox, all in one transaction.

Inventory: batches, ledger, balances, counts

Responsibility. The only module that changes stock. Every change is a stock_movement row, and stock_balance is updated in the same transaction as the projection (INV-04).

Public APIallocateAndDeduct(AllocationRequest), receive(ReceiveBatchCommand), adjust(...), returnToBatch(...), availableBatches(skuId, locationId)
PublishesStockLow, BatchNearExpiry, StockWentNegative, StockAdjusted
ConsumesGoodsReceived (purchasing), TransferShipped/TransferReceived (R2)
JobsNightly ledger check: rebuild balances from movements, report drift. Daily expiry scan.
Movement typesRECEIPT, SALE, RETURN, ADJUST_IN, ADJUST_OUT, COUNT_CORRECTION, TRANSFER_OUT, TRANSFER_IN, SUPPLIER_RETURN, WRITE_OFF_EXPIRED
Catalog: products, SKUs, barcodes, units

Responsibility. Master data for what can be sold. Products have variants, and every sellable thing is a SKU with one or more barcodes. Units and conversions are defined here (box → pieces).

Public APIfindSkuByBarcode, getSku, importProducts(file) (async job), exportProducts
PublishesProductChanged, SkuChanged, BarcodeChanged. Each change also writes sync_change_log rows.
SPIProductAttributeProvider (extensions add fields such as generic name or PLU)
Item typesSTOCKED, SERVICE (no stock, e.g. salon), WEIGHED, NON_INVENTORY
Pricing: price lists, discounts, promotions

Responsibility. Holds the price for a SKU per branch and price list (retail, wholesale), including batch-level prices. Discount limits per role. Promotions (R2) are rules evaluated by the same logic on the register and the server.

Public APIpriceFor(sku, branch, priceList, batch?), validateDiscount(user, amount)
SPIPricingRule (e.g. happy hour, mix & match from extensions)
NoteA sale arriving from a register is not repriced. The server compares prices and raises a PRICE_MISMATCH exception if they differ.
Payments: payment types, split payments, refunds

Responsibility. Records how a sale was paid: cash, card, LankaQR, customer credit, and later gift card and loyalty points. In the MVP card and QR store only a reference and the last 4 digits from the terminal slip (INV-11).

SPIPaymentProvider (R3: semi-integrated terminal, LankaQR dynamic QR)
PublishesPaymentRecorded, RefundRecorded
Cash: shifts and cash-up

Responsibility. Opening float, cash in/out (petty cash, safe drops), blind count at close, expected vs counted, shortage and overage. One open cash session per register.

ConsumesSaleCompleted, RefundRecorded (cash totals per session)
PublishesShiftClosed (with variance), CashVarianceExceeded
Customers: profiles, credit, loyalty

Responsibility. Customer records with minimal personal data. Credit accounts use their own ledger (sale on credit = debit, settlement = credit). Loyalty points follow in R2.

ConsumesSaleCompleted (credit debit, purchase stats), SaleReturned
PublishesCreditLimitExceeded, CreditSettled
Tax: rates, invoices, credit notes, fiscal adapter

Responsibility. The only place tax is calculated and tax documents are issued (INV-07). Owns tax rate rules with valid-from dates, tax invoice series, credit and debit notes, and the fiscal adapter port.

Public APIcalculate(lines, branch, date), issueDocument(sale), issueCreditNote(return)
PortFiscalGateway: NoopFiscalGateway (MVP), RamisEInvoiceGateway (R3), SecuredPosGateway (R3, spec pending)
PublishesTaxDocumentIssued, FiscalSubmissionFailed
RuleSubmitted documents are never changed. Corrections are new documents (IRD practice for RAMIS).
Sync: register pull and push

Responsibility. Serves change feeds and catalog snapshots to registers, and accepts batches of sales, returns, cash events and audit entries. Owns the idempotency inbox. Contains no business rules: it delegates to Sales, Cash and Audit.

See Offline & sync for the full protocol.

Reporting: read models

Responsibility. SQL views and materialized views (mv_daily_sales, mv_stock_valuation, mv_expiry), refreshed by the worker. Uses the read replica when one exists. It may read other modules' tables through views only, which is the one documented exception to INV-08.

Tenancy, IAM, Audit, Devices (platform)
  • Tenancy resolves the tenant from the token and sets app.tenant_id for RLS on every transaction. It stores per-tenant settings, enabled modules and the shop's plan. The plan catalog in code sets each plan's limits and features; a check returns PLAN-001 when something isn't included (Plans).
  • IAM: users, roles, permissions, password and MFA, refresh token rotation, staff PIN hashes for registers.
  • Audit: AuditApi.record(event) appends a hash-chained entry. Registers push their local audit entries through Sync.
  • Devices: enrollment codes, device keys, heartbeat (app version, queue depth, printer status, last sync), remote lock.
