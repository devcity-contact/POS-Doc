Business rules to enforce

RuleWhat it enforces
BR-01Discount limit per role, with a recorded manager override
BR-02Price, discount, tax and batch cost snapshot on every sale line
BR-03Calculate to 4 decimals, round HALF_UP to 2
BR-04Chosen or scanned batch, else FEFO
BR-05Short stock never blocks an offline sale; the server raises an exception
BR-06Returns limited to what was bought, within the return window (14 days by default)
BR-07Credit sales need a credit customer; over the limit needs a manager
BR-08No sale without an open shift
BR-09Expired batches cannot be sold
BR-10Gap-free receipt and tax invoice numbers per register
BR-11Tax from rules with valid-from dates, never hard-coded

Infrastructure and operations

  • Database and storage: PostgreSQL 18 with row-level security on every tenant table (INV-01); point-in-time backups and a daily off-site copy; object storage (MinIO or S3) for snapshots, imports and exports; transactional e-mail for invitations and password resets only.
  • Delivery: Docker containers, a CI/CD pipeline, a module-boundary test and a tenant-isolation test in CI.
  • Run-time: monitoring and alerts, runbooks, and a quarterly restore drill. Details: Deployment and Monitoring & runbooks.

The register app itself must also handle:

  • Offline: at least 72 hours of selling with no connection, at least 10,000 queued sales, and an outbox with retry (NFR-03).
  • Search: local search over 50,000 products in under 100 ms (NFR-01).
  • Barcodes: GS1 2D codes, plus scale barcodes with the weight or price inside.
  • Printing: ESC/POS receipts in English, Sinhala and Tamil, and the drawer kick.
  • Input: keyboard F-keys and touch.

Points to watch

Read before planning
  1. Android is in the MVP (F-708) for the mobile Lite plan. The same React UI goes into the Capacitor shell, plus a phone-sized Sell screen, camera scanning and a Bluetooth/USB printer plugin. Test on a short list of reference phones, tablets and Bluetooth printers; device variety is the main risk.
  2. The prototype shows a few R2 extras that are not part of the MVP: e-mailing receipts and statements, SMS to buyers during a recall, and loyalty points.
  3. Pharmacy and grocery modules are R2, but their basics are core MVP: batches, expiry, FEFO, generic-name search and scale barcodes.

Build order

Database first: create all 56 tables in four migrations (store & staff, catalog, inventory, sales) before the features, as described in Data model › Build order, with the whole-database diagram. Then build the features in the phase order below. Every task (backend, admin and register screens, and a Try it check per stage), in order and with tick boxes to track progress, is in the build order.

From the roadmap. The phases add up to about 54 weeks: roughly 11–13 months for one engineer, or 8–9 months with a second engineer from phase 4.
